# Аналитика и избранное InviteIZI

Изменения встроены в существующие webhook, Repo, PostgreSQL, обработку чеков и персональные ссылки. Новый бот или отдельный аналитический сервис не создаются.

## Перед включением

1. Применить `supabase/migrations/20261025120000_analytics_favorites.sql` после предыдущих миграций проекта. Не запускать заново исходную схему на рабочей базе.
2. В окружении сервера задать `OWNER_TELEGRAM_ID`: числовой Telegram ID владельца. Имя пользователя не используется для выдачи прав. Для подтверждения чеков владелец должен также оставаться в существующих `ADMIN_IDS` / `admins`.
3. Если нужны другие аналитики, добавить их в существующие администраторы и указать в `ANALYTICS_ADMIN_IDS` либо установить `admins.can_analytics = true`. По умолчанию право выключено.
4. Задать `ANALYTICS_SIGNING_SECRET`: отдельную случайную строку длиной минимум 32 символа. Без неё сбор открытий демо выключен; оформление заказов продолжает работать. Секрет никогда не добавлять в Git или отчёт.
5. Развернуть код. Проверить `/dashboard`, `/stats`, `/orders` в личном чате с ботом. При необходимости обновить список клиентских команд существующим скриптом настройки Telegram; `/favorites` включён в обе локализации.

Без доступа к рабочему окружению эти настройки и миграция в Supabase в рамках данной работы не применялись.

## Права

- `/dashboard` и callbacks `dash:*` повторно проверяют права при каждом обращении.
- `/customers` и раздел «Клиенты» доступны только `OWNER_TELEGRAM_ID`.
- Ограниченный администратор не получает имена покупателей даже в SQL-проекции общего отчёта.
- Общие отчёты возвращают агрегаты. Личный отчёт содержит только имеющиеся имя/username, число и сумму покупок, последнюю дату и частые категории. Адреса, чеки, телефоны и тексты приглашений туда не загружаются.
- Аналитика, избранное и команды поиска/заказов не публикуются в групповых чатах.
- Публичного HTTP-маршрута чтения аналитики нет. PNG отправляется байтами напрямую через существующий `Tg.sendPhoto`.
- Новые таблицы закрыты для Supabase `anon` и `authenticated`; доступ имеет серверная роль.

## Определения показателей

- День — календарный день Asia/Almaty (UTC+5). Семь/тридцать дней включают сегодняшний день и предыдущие 6/29 дней; конец периода — момент отчёта.
- Заказы считаются по `created_at`; выручка и оплаченные заказы — по `paid_at`, только в `active`/`archived`. Для старых записей без `paid_at` сохранён существующий резервный вариант `updated_at`: точную историческую дату оплаты таких записей восстановить нельзя.
- Из-за разных дат заказов и оплат в одном периоде число оплат может превышать число новых заказов.
- Средний чек = подтверждённая выручка / число оплаченных заказов. Неоплаченные включают все статусы, кроме `active`/`archived`; ожидающие чеки и отказы также показаны отдельно.
- Повторный покупатель — покупатель выбранного периода с более чем одной подтверждённой покупкой за всё время. Персональный TOP-10 показывает покупателей периода с их пожизненными итогами.
- Аналитика музыки читает сохранённый выбор заказа; названия ищутся во всей таблице музыки, включая скрытые записи. Статистика не предоставляет ссылки на прослушивание скрытых треков. Доля встроенной/своей считается среди заказов с музыкой, безмузыкальные показаны отдельно.
- Финансовые счётчики не суммируют события. События создания заказа/первого подтверждения записываются триггером в той же транзакции и имеют уникальный ключ заказа.
- Просмотры каталога не собираются и не заменяются числом заказов.
- `demo_opened`: только переход по выданной ботом ссылке и последующее реальное pointer/keyboard-взаимодействие на видимой странице; один пользователь/дизайн/день. Это нижняя оценка, а не все посетители сайта. Пересланная ссылка остаётся той же capability; она не идентифицирует нового гостя. Обычный GET, link preview, префетч и перезагрузка сами событие не создают.
- Маркер демо зашифрован AES-GCM, истекает через 24 часа и передаётся во фрагменте `#dt=…`, который не отправляется серверу в URL/Referer. После загрузки фрагмент удаляется. Принимающий POST проверяет origin, размер тела, маркер и известные preview-боты. Маркер даёт только право записи одного ограниченного события, не доступ к статистике.
- `design_selected` защищён ключом пользователь/дизайн/номер вопроса. Конверсия дизайна — доля уникальных выбравших его клиентов периода, затем создавших подтверждённый заказ на этот дизайн к моменту отчёта. Исторические продажи без соответствующего выбора знаменатель не заменяют.
- Избранное сохраняется парой пользователь/дизайн. Аналитика добавления — уникальные первые добавления пары за всё время; удаление и повторное добавление не увеличивают этот показатель.
- Воронка показывает отдельные счётчики этапов после старта трекинга, а не строгую сквозную сессию. Исторические просмотры и выборы не восстанавливаются. Начало сбора хранится в `analytics_config` и показано в отчёте.
- График выручки «Всё время» показывает последние 30 дней, а сумма над ним — весь период. Остальные графики используют выбранный период. Для нулевых данных изображение сообщает «Пока недостаточно данных».

## Демо и превью

Персональное демо истекает ровно через 24 часа с `created_at`, независимо от редактирования и отправки чека. Подтверждённая оплата открывает ту же ссылку до действующего срока мероприятия + 30 дней. Статическое каталожное демо не является персональным и не истекает.

OG использует только имена/название события, дату и отдельную обложку без примерных имён и адресов. Изображения обложек создаются из имеющихся материалов командой `node scripts/make-og-covers.mjs`. Шрифты отчётов и OG локальные, с OFL-лицензией.

Ответ генератора OG имеет `Cache-Control: no-store`, но Telegram/WhatsApp могут хранить собственную карточку дольше. Мгновенное обновление после правок не гарантируется; основной URL и маршруты сохранены.

## Проверка

- `npm test`: сценарии старого бота + новые права, деньги, избранное, трекинг, музыка, PNG и локальная SQL-миграция на PGlite.
- `npm run test:pg`: существующие интеграционные тесты против выделенной PostgreSQL-базы. Не подменять ими тесты на рабочей базе с реальными клиентами.
- `npm run lint`, `npx tsc --noEmit`, `npm run build`.
- `node scripts/check-mobile-regression.mjs` против локального production-сервера: все принятые дизайны на 360/375/430 px.
- `CHECK_LONG_ONLY=1` и `CHECK_BASE_URL` dev-сервера: длинные данные на 375 px; существующий `/long` закрыт в production.

Для значительного роста базы следует перенести агрегирование из минимальной серверной выборки в SQL; текущая реализация читает финансовую проекцию заказов, пользователей и событий в согласованном snapshot. Новые сторонние сервисы не используются.
