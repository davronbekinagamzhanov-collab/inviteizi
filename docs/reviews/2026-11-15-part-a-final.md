## 5. Скорость

Замер Lighthouse 12.6 (мобильный профиль), локальная production-сборка, страница `/demo/<id>`.
«Медленный 4G» — штатный профиль Lighthouse (1,6 Мбит/с, RTT 150 мс, процессор ×4).
«Обычный 4G» — 9 Мбит/с, RTT 100 мс, процессор ×4 (средний Android). 49 дизайнов: 10 первых в каталоге (данных о заказах
в репозитории нет, рабочую базу не трогали), все 21 новый и «лагающие» из `docs/reviews/stage3-analysis.md`.

**Итог.** Медленный 4G: первый экран в среднем 6,2 → 4,5 с, LCP 11,7 → 6,7 с, вес 1 683 → 1 081 КБ.
Обычный 4G после правок: первый экран в среднем 1,4 с, LCP 1,8 с; **цель «первый экран быстрее 2,5 с» выполнена
у 48 из 49** (LCP ≤ 2,5 с — у 47). Не уложились только скрытые дизайны: `oltin-ot` (5,8 с — шрифт Merriweather 2,4 МБ
с Reserved Font Name, без переименования его урезать нельзя) и `ganch-peshtoq` (LCP 2,6 с).

Что сделано (вид не меняется):

1. **CSS только своего дизайна.** Реестр содержал `import()` всех 107 дизайнов, и каждая страница тянула ~79 файлов
   CSS и все `@font-face`. Реестр теперь только данные, код дизайнов — в `templates/design-modules.ts`, страницы
   берут `DesignView` с `next/dynamic`. На странице 4–5 файлов CSS вместо 79.
2. **Шрифты.** Корневая страница «не найдено» предзагружала Cormorant и PT Serif на каждой странице (~305 КБ) — выключено.
   Web-копии шрифтов (`assets/fonts/web`): шрифты OFL без Reserved Font Name урезаны до латиницы, всей кириллицы
   с узбекскими и казахскими буквами и знаков; ось ширины закреплена (`font-stretch` нигде не используется).
   Lora и PT Serif только переупакованы TTF → WOFF2 без изменения глифов. 11,2 → 5,4 МБ, Playfair 638 → 284 КБ.
3. **Картинки.** 21 картина пережата в WebP q82 — только где экономия ≥ 15 % и PSNR ≥ 38 дБ.
4. Уже было и проверено: музыка не запрашивается до открытия (`preload="none"`, в замерах 0 запросов),
   картинки ниже первого экрана — `loading="lazy"`, `prefers-reduced-motion` учитывается (`MotionConfig reducedMotion="user"`).

Пример по типам ресурсов (`muhr`, медленный 4G): шрифты 784 → 368 КБ, JS 458 → 238 КБ, CSS 146 → 47 КБ.

Анимации открытия отдельно не переделывались: время блокировки основного потока (TBT) снизилось
у большинства дизайнов за счёт меньшего объёма CSS и JS. Проверка плавности на реальном телефоне — в списке ручных проверок.

## 6. Безопасность (проверка «как атакующий»)

| Что проверено | Результат |
|---|---|
| Подделка Telegram initData | Подпись HMAC по токену бота, сравнение за постоянное время, срок 24 ч, проверка id (`lib/tg-init-data.ts`). Без верной подписи — 401. |
| Админка, панель менеджера/партнёра через URL | Страницы `/app/owner`, `/app/panel` — пустые оболочки; все данные только через `/api/app` с проверкой роли по initData на сервере (`ownerPanel` → `isAdmin`, `rolePanel` → менеджер/партнёр). Параметры URL роли не дают. |
| Прямые API-запросы к чужим заказам (подмена id) | `editOrder`, `confirmPay`, `cancelOrder`, `saveDraft`, `submitDraft` сверяют `order.userId` с пользователем initData → `notFound`. |
| Кнопки бота с чужим номером заказа | `edit/link/rsvp/pay/rcpt/fix/rv` — через `ownOrder` (владелец заказа); `ok/no/nr` — `guardAdmin`; `po/mp/dp/ex/st/sm/pa/pn/cl/dash` — проверка роли. Новые сценарные тесты это подтверждают. |
| НАМУНА, ответы RSVP, партнёрская статистика | НАМУНА — по ссылке (так задумано: её отправляют гостям). Ответы RSVP показываются только владельцу заказа в боте. Партнёр видит только свои суммы, без имён и ссылок клиентов (тест). |
| Подмена цены, формата, дизайна из браузера | Сумма считается на сервере по формату (`PRICES`), смена дизайна — только на дизайн в продаже того же формата; скрытый дизайн для нового заказа отклоняется (тест). |
| Промокоды, повтор, бесплатный заказ в обход оплаты | Промокоды PR #20: атомарные лимиты и резервы в PostgreSQL, 19 тестов на изолированной базе (включая параллельные заказы). 0 ₸ — только через серверный сценарий промокода, без фиктивной оплаты Kaspi. |
| XSS через имена, адреса, пожелания | React экранирует текст; `dangerouslySetInnerHTML` нигде нет; бот шлёт простой текст без `parse_mode`; ссылка на карту — только https и только с доменов карт; Excel — XML-экранирование, ячейки строковые (формулы не исполняются). |
| SQL-инъекции | Все запросы — параметры postgres.js; `sql.unsafe` только для постоянных списков колонок. |
| Секрет вебхука Telegram | Заголовок `X-Telegram-Bot-Api-Secret-Token`, сравнение за постоянное время; `/api/cron` — секрет в базе. В Preview `/api/bot`, `/api/app`, `/api/rsvp`, загрузки отвечают 404. |
| Лимиты частоты | RSVP — по хэшу IP в базе; постер партнёра — раз в минуту. **Найдено:** загрузки (подписанная ссылка на песню до 20 МБ, фото, чек) и действия Mini App без лимита — один пользователь мог забивать хранилище. **Исправлено:** `lib/rate-limit.ts` (90 действий/мин, 6 ссылок на песню и 20 загрузок за 10 мин на пользователя, ответ 429). Лимит «мягкий» — в памяти экземпляра функции. |
| Утечка секретов в клиентский код | В собранных браузерных файлах нет токенов, паролей, `service_role`, JWT; `NEXT_PUBLIC_*` не используется; клиентские файлы не импортируют `lib/env` и `lib/db`. |

Остаточные риски (не исправлялись, решение владельца):

- Партнёр, созданный по @username без Telegram ID, привязывается к первому, кто откроет панель с этим username
  (один раз). Если партнёр сменит username до первого входа, а кто-то займёт старый — доступ получит он.
  Надёжнее создавать партнёров через ссылку `join_`.
- Ограничитель частоты в памяти экземпляра: при многих экземплярах Vercel суммарный лимит выше. Строгий —
  только через таблицу в PostgreSQL (отдельная задача).
